# 决策记录：工作项驱动生命周期（Work-Item-Driven Lifecycle）与按需托盘

**日期**：2026-08-25
**决策**：平台生命周期由“工作项”驱动，而非“窗口数”驱动；系统托盘图标仅在存在后台驻留应用时动态出现（普通场景无托盘驻留）。
**状态**：已采纳（ADR-010）
**关联**：修订 ADR-005（常驻进程）、ADR-002/ADR-009（模式 A 独立 profile）；影响 §2.3、§2.10、§3.1

---

## 用户理想（转述）

1. 不想要平台进程在系统托盘常驻一个小图标（“管理界面不会驻留小图标那里”）。
2. 平台生命周期：
   - **第一个 web app 启动 → 平台随之启动**；
   - **最后一个 web app 关闭 → 平台随之关闭**。
3. 顾虑：需要 Ctrl+C 退出的 web app（有 postExit 钩子善后）全退时能自然退出；但“默认什么都不做就退出”的普通 app，若将来需要其后台驻留，当前模型没有空间——感觉“绕”。

## 为什么“窗口数驱动”不成立（矛盾分析）

用户原理想“平台随最后一个窗口关闭而退出”，与需求 2.3“后台持久化驻留”（窗口关了进程还活着）**正面冲突**：

- 有驻留型 app（窗口关、进程在后台）时，平台若随最后窗口退出 → 驻留 app 变**孤儿**：无人管理、无入口唤出、模式 B 渲染器随平台消亡被杀。
- 若平台为承载驻留而常驻 → 违背“随用随走”，且回到“常驻托盘图标”的老问题。

“默认什么都不做就退出”的 app 想驻留时同样卡住：平台要么为它永远常驻，要么它一关窗口就死——两头不对。

## 解法：平台生死的判定 = “是否还有需要平台活着的工作项”

**自动退出条件（三者全空）**：

1. 无存活的后台驻留型应用（窗口已隐藏、进程仍在后台运行）；
2. 无执行中的钩子任务（postExit 正在善后）；
3. 管理控制台未打开。

只要任一项非空，平台保持存活（CPU≈0、内存<50MB、无托盘图标）；全部清空则走退出流程。

### 退出流程（按序善后，避免“绕”）

```
判定可退出（工作项全空）
  → 执行所有存活 postExit 钩子（等待完成，可超时）——Ctrl+C 型 app 借此自然停后端
  → 终止所有模式 B 渲染器 / 关闭模式 A 独立 profile
  → 平台进程退出
```

- postExit 钩子必须**在平台退出前跑完**（或超时），否则 Ctrl+C 型 app 的善后会被平台退出生硬打断——这正是用户“全退了自然退出”的要义。
- 平台退出前若仍有驻留型 app → **不满足退出条件**，继续活着。

### 托盘：按需动态出现（用户选定）

- **默认无托盘图标**（满足“不要常驻小图标”）。
- 仅当**存在后台驻留应用**时，托盘图标动态出现，提供：驻留应用列表、唤出、终止、“显示主面板”。
- 全部驻留应用结束后，图标消失（回到无托盘状态）。
- 非驻留场景的唤出/管理走**桌面快捷方式**（双击 `WebDesk 控制台` / 应用快捷方式 → IPC 激活或拉起平台），不依赖托盘。

## 对既有决策的影响

| 决策 | 修订 |
|---|---|
| ADR-005（常驻进程） | 保留“常驻进程、非 Windows Service”；补充：常驻但不渲染托盘，生命周期由工作项驱动 |
| ADR-004（后台驻留） | 驻留型 app 是“让平台保持存活”的工作项之一；退出判定纳入 |
| §3.1 资源占用 | 后台驻留时平台仍须 CPU≈0 / 内存<50MB（无感驻留） |
| §2.10 系统托盘 | 改为“按需动态出现”（有驻留 app 时）；默认无图标 |

## 边缘情况

- **平台退出后，用户再点某 app 快捷方式** → 启动器检测主进程不存在 → 拉起平台 → 启动该 app（原 2.6 调度逻辑不变）。
- **全部驻留 app 结束后**，若控制台恰好打开 → 平台仍存活（控制台是工作项）；关闭控制台且无其它工作项 → 退出。
- **钩子执行中**（如 postExit 正在善后）→ 平台不退出，等钩子完成/超时。
- **平台自身更新/安装** → 需在无工作项时进行，或先停所有 app。

## 对“管理控制台 = 第一个应用”的一致性

控制台是一个普通 web app（模式 B）；其窗口关闭且无其它工作项时，平台同样退出——控制台不特殊，只是另一个可被快捷方式唤出的应用。平台“无感存在”时，控制台也只是一条快捷方式。
