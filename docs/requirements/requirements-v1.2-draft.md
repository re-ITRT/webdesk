## 1. 项目背景与目标

### 1.1 背景

随着云计算与 SaaS 服务的普及，用户日常依赖的办公、协作及管理工具逐渐迁移至 Web 端。然而，当前浏览器标签页式的管理方式存在入口分散、资源占用高、缺乏系统级生命周期管理等问题。传统的 Electron 封装方案虽然解决了入口问题，但包体过大、版本更新滞后、且无法灵活利用本机 Chrome 的调试及插件生态。

### 1.2 目标

本项目旨在构建一个**轻量级、高可控性的 Web 应用桌面化运行与管理平台**。该平台将 Web 应用以“原生桌面应用”的形态呈现，同时提供深度的生命周期钩子、后台驻留能力及高度自由的界面定制功能，最终实现通过系统桌面快捷方式一键直达 Web 服务。

### 1.3 产品定位

对标：WebCatalog（自有引擎，不支持复用系统 Chrome 登录态的双模）、Fluid/Coherence（仅 macOS）、Ferdium（多应用挤单一窗口）、Electron 包装（重）。**差异化 = 双模引擎 + 生命周期钩子 + 托盘级生命周期管理** 的组合，Windows 优先。

## 2. 功能性需求

### 2.1 按应用独立配置的双模渲染引擎

平台应提供两种渲染模式，且**核心设计原则为：每种模式针对单个 Web 应用独立生效，而非全局开关**。用户可根据不同 Web 应用的特性、安全等级或性能需求，为其单独指定最合适的运行模式。

| 模式 | 说明 | 适用场景举例 |
| :--- | :--- | :--- |
| **模式A（系统原生调用）** | 调用本机安装的 Google Chrome 浏览器，通过特定命令行参数（如 `--app`）启动独立窗口。 | 个人常用的轻量级服务（如在线文档、个人管理面板），希望复用本机 Chrome 已登录的账户状态、书签及偏好设置。 |
| **模式B（内置运行时）** | 使用平台内置的 WebView2 运行时。该环境独立于系统浏览器。 | 工作专用的后台管理系统，需隔离个人浏览记录与工作记录；或运行依赖特定版本浏览器特性的老旧 Web 应用。 |

**配置粒度要求**：

- 在平台管理界面的“应用编辑”页面中，必须提供**独立的渲染模式单选按钮**，供用户为每个应用单独切换。
- 当用户通过桌面快捷方式启动应用时，平台调度器会**读取该应用专属的配置项**，决定本次启动调用系统 Chrome 还是内置 WebView2 内核。
- 同一时刻，运行中的应用 A（模式A）与应用 B（模式B）可以**共存**，互不干扰。

#### 2.1.1 模式 A 控制深度界定（V1.2 新增决策）

> **背景**：模式 A 要“深度控制”（CSS/JS 注入、隐藏导航栏、按应用扩展）必须依赖 Chrome DevTools Protocol（CDP）。但 CDP 调试端口 = 本机任意进程可接管该浏览器；且 Chrome 扩展是 **per-profile 而非 per-window** 的，无法做到“不同应用、不同扩展集”。若强行在模式 A 上做深度定制，实现复杂度与安全风险会不成比例地上升。

**决策：模式 A = “轻控制”**。平台对模式 A 应用只承诺以下能力：

1. **启动**：`chrome.exe --app=<url>` 启动独立窗口；
2. **定位/激活**：按窗口标题查找 HWND，支持托盘唤出、任务栏激活；
3. **终止**：仅针对独立 profile 实例的进程树终止（见 2.3.2）；
4. **生命周期钩子**：启动前 / 关闭后钩子照常生效。

**模式 A 明确不承诺（V1.2 新增）**：

- ❌ CSS/JS 注入（`webContents.executeJavaScript` 类能力）——模式 B 才提供；
- ❌ 按应用扩展隔离——Chrome 扩展是 profile 级，模式 A 无法按窗口隔离；
- ❌ 隐藏浏览器原生导航栏的深度控制——依赖 CDP，不纳入模式 A。

> **用户决策提示**：若产品确实需要在系统 Chrome 上做深度定制，可改为“独立 profile + CDP”，但需接受【丢弃“复用本机登录态”卖点】+【开放调试端口的安全风险】两项代价。当前默认不选。

#### 2.1.2 模式 B 内核选型（V1.2 新增决策）

**决策：模式 B 使用 Microsoft WebView2**（Edge Chromium 运行时），而非打包完整 Chromium（约 300MB+，违背轻量目标）。

| 运行时档位 | 说明 | 适用 |
|---|---|---|
| **Evergreen**（默认） | 复用系统已装的 WebView2 运行时（Win11 随系统自带，Win10 基本随 Edge 安装）。平台包体接近零体积。 | 绝大多数应用 |
| **Fixed Version** | 随平台分发指定版本的 WebView2 运行时（约百 MB 级）。版本由平台发布机制控制。 | 依赖特定版本特性 / 需锁版本的老旧应用 |

**要求**：`renderEngine: "embedded"` 的配置条目中，应额外包含 `runtimeProfile` 字段（`"evergreen" | "fixed"`），**per-app 可切换**，默认 `evergreen`。

### 2.2 生命周期钩子（Lifecycle Hooks）

系统应允许为每一个独立的 Web 应用配置脚本化的“事件钩子”，实现真正的环境联动。

- **启动前钩子（Pre-Launch Hook）**：在 Web 窗口弹出之前执行。场景包括自动建立 SSH 隧道、启动 WSL 中的后端服务、设置环境变量、或唤醒本地数据库。
- **关闭后钩子（Post-Exit Hook）**：在 Web 窗口被关闭后执行。场景包括自动终止由启动钩子触发的进程（如发送 `Ctrl+C` 信号）、清理临时文件、或释放端口资源。
- **进程监控机制**：钩子命令的执行状态应被平台监控，支持阻塞式启动（等待钩子执行完毕再加载页面）。

**V1.2 补充（钩子执行协议）**：

- 钩子由**后台服务进程**执行（不依赖管理界面存活）。
- 每个钩子支持配置：**执行环境**（`cmd` / `powershell` / `wsl`）、**超时**（默认如 30s，超时强制终止并标记失败）、**阻塞/非阻塞**（阻塞=等钩子完成再加载页面；非阻塞=后台异步执行）。
- 钩子输出（stdout/stderr）与退出码**落盘为日志**，便于排障。
- 进程树回收：钩子启动的子进程需可被整体终止（`taskkill /T`；WSL 进程组单独处理）。

### 2.3 后台持久化驻留（Background Persistence）

解决“关闭窗口即退出应用”的传统网页痛点。

- **窗口关闭拦截**：当用户点击窗口关闭按钮（X）时，平台应提供“最小化至系统托盘”或“后台继续运行”的选项，而非直接终止进程。
- **后台网络保活**：确保 Web 应用在窗口隐藏状态下仍能维持 WebSocket 连接或执行后台同步任务。
- **托盘管理**：系统托盘区应驻留平台图标，展示当前正在后台运行的应用列表，用户可随时通过托盘“唤出”隐藏的窗口或“彻底终止”应用。

#### 2.3.1 后台驻留机制（V1.2 澄清）

> **背景**：原 V1.1 写“启用 `--enable-background-networking` 标志确保 WebSocket 存活”，此表述不准确——该标志是 Chrome 后台网络调度的系统级开关，**不是**给任意 Web 应用保 WebSocket 用的。

**V1.2 决策——按模式分机制**：

- **模式 B（WebView2）**：关闭窗口 = **隐藏 WebView2 渲染器（`Hide`）但不销毁**。渲染进程继续存活，WebSocket/后台任务自然保活。这是最可靠的后台驻留机制。
- **模式 A（系统 Chrome）**：`--app` 独立窗口关闭后进程即退出，**无法**通过“隐藏”保活。模式 A 的“后台驻留”语义 = 仅当使用**独立 profile** 时，可尝试 `chrome --app` 以最小化/隐藏方式启动并驻留；默认场景下**关闭 = 退出**（文档需向用户明示此差异）。

#### 2.3.2 “彻底终止”模式 A 应用的边界（V1.2 澄清）

Chrome 的 browser 进程是**共享**的：同 profile 下多个 Chrome 窗口/应用共用一个进程树。直接杀进程会误伤用户其它 Chrome 窗口。

**V1.2 决策**：平台对模式 A 的“彻底终止”仅作用于**该应用对应的独立 profile 实例**；若应用运行在用户日常 profile（共享）中，平台**不提供强制杀进程**，而是提示用户手动关闭窗口，或引导切换至模式 B。

### 2.4 界面及功能栏高度定制化

满足不同 Web 应用对界面控件依赖度的差异。

- **浏览器原生控件开关**：提供针对单个应用的配置开关，允许用户独立控制是否显示“地址栏”、“前进/后退”、“刷新”等原生导航按钮。

  > **V1.2 界定**：此能力**仅在模式 B** 完整承诺（WebView2 可自由控制 UI 控件）；模式 A 仅能控制启动时是否显示地址栏（`--app` 默认无地址栏，`--app` 加显式窗口可带）。

- **自定义脚本注入（CSS/JS）**：允许高级用户在应用加载时注入自定义样式或脚本，用于移除或修改 Web 应用内固有的 UI 元素、注入第三方接口调用的快捷操作按钮等。

  > **V1.2 界定**：**仅在模式 B** 承诺（模式 A 见 2.1.1）。注入内容运行于应用源域、能读写应用数据——文档须加**安全风险提示**（见 3.4）。

- **扩展程序（Extension）按需加载**：允许用户针对每一个 Web 应用配置独立的已启用扩展列表，实现“不同应用、不同插件集”的隔离。

  > **V1.2 界定**：**仅在模式 B** 承诺（WebView2 支持 per-environment extension 管理）；模式 A 因 Chrome 扩展为 profile 级，无法按窗口隔离，不承诺。

### 2.5 桌面快捷方式入口（Launcher Entry）

实现“原生应用”般的启动体验，无需每次通过主界面查找。

- **一键创建快捷方式**：在平台管理界面中，用户右键或点击“发送到桌面”时，系统应生成一个标准的操作系统快捷方式文件（`.lnk`）。
- **启动指令协议**：快捷方式的启动目标应遵循特定格式（例如：`WebDesk.exe --launch [应用唯一标识符]`）。
- **轻量化启动器**：平台主程序在接收到 `--launch` 参数启动时，应具备极短的响应时间。

**V1.2 补充**：建议拆出一个**数百 KB 级的独立启动器**（`WebDesk.Launcher.exe`）与主服务解耦——双击快捷方式时启动器只做“检测主进程存活 → 存活则 IPC 转发并退出 / 未存活则拉起主服务”，响应更快、与主服务版本无关。

### 2.6 单例模式与进程调度（Singleton & Scheduler）

解决“多开”与“资源冗余”问题。

- **唯一实例**：无论用户点击多少次快捷方式或主程序图标，系统内只允许存在一个平台主进程（或后台服务进程）。
- **进程间通信（IPC）与指令转发**：若平台主程序已在后台运行，用户双击桌面快捷方式时，新启动的进程应不创建新实例，而是通过 IPC 将 `--launch` 指令“转发”给正在运行的主进程，随后自身立即退出。主进程接收指令后，若该应用窗口已存在，则将该窗口激活；若不存在，则读取该应用配置的渲染模式，执行创建流程。

**V1.2 补充（实现机制）**：单例用**命名互斥体（Named Mutex）**；IPC 用**命名管道（Named Pipe）**；启动器/主服务间指令协议需包含应用唯一标识与动作类型（`launch` / `activate` / `terminate`）。

### 2.7 内置默认应用：管理控制台（Web 形态）（V1.3）

**决策：管理界面不采用原生桌面框架（WPF），而是以 Web 应用形态交付，并作为平台启动时预置的首个默认应用。**

- **形态**：后台服务内嵌本地 HTTP 服务器（仅绑定 `127.0.0.1`），同时托管管理 API 与静态控制台资源；控制台是一个注册在应用列表里的内置 Web 应用（`renderEngine: "embedded"`，URL 指向本机端口）。
- **首个默认应用**：平台安装后即存在一个预置应用“WebDesk 控制台”，用户可像管理任何其它应用一样管理它（改注入、设钩子、配扩展）；可删除，但可通过管理 API 恢复重建。
- **吃自己的狗粮**：控制台自身就运行在平台上，平台每一处能力（渲染、注入、钩子、后台驻留、托盘唤出）都被控制台日常调用，既是功能又是持续的自测。
- **恢复通道**：当内置渲染（模式 B）异常时，控制台仍可经普通浏览器打开 `http://127.0.0.1:<port>` 访问——本地 HTTP 同时充当故障恢复路径。
- **原生壳收窄**：仍保留原生能力的仅有：托盘菜单、系统通知、桌面快捷方式、单例/IPC、钩子执行、Chrome 探测与模式 A 启动、Job Object 进程回收——即“原生内核（daemon）+ 全 Web 界面”。

## 3. 非功能性需求

### 3.1 资源占用

- **空闲状态**：当无 Web 应用运行或仅后台驻留时，主进程 CPU 占用率趋近于 0，内存占用控制在 50MB 以内。
- **启动响应**：从双击快捷方式到 Web 窗口渲染完成（含钩子命令执行时间），视觉响应延迟应控制在用户可接受范围内（目标：启动器转发 < 100ms，窗口出现 < 2s，不含钩子）。

### 3.2 兼容性

- **操作系统**：优先支持 Windows 10/11，后续可扩展至 macOS。
- **命令行环境**：钩子脚本需支持 `CMD`、`PowerShell` 以及 WSL Linux 子系统三种 Shell 环境。
- **Chrome 版本探测**：对于模式A，平台需具备自动检测本机 Chrome 安装路径及版本号的能力（注册表 HKLM/HKCU/WOW6432Node + App Paths 双保险），并在检测失败时给予清晰提示，引导用户切换至模式B。

### 3.3 配置持久化

- **配置文件**：所有应用配置应以结构化文本（如 JSON 或 YAML）存储。每个应用的配置条目中，应明确包含 `renderEngine` 字段，值为 `"system"` 或 `"embedded"`，以支持迁移与备份。
- **V1.2 补充**：配置文件根目录建议 `%APPDATA%\WebDesk\config\`；需提供**导出/导入**能力（备份与迁移）；`renderEngine:"embedded"` 条目另含 `runtimeProfile` 字段（见 2.1.2）。

### 3.4 安全与风险（V1.2 新增）

- **注入脚本风险提示**：注入的 CSS/JS 运行于应用源域，可读取应用数据。管理界面需在注入编辑器处展示明确风险提示（“仅向可信应用注入”）。
- **CDP 风险**：若未来启用模式 A 深度控制（CDP），调试端口使本机任意进程可接管浏览器，需评估鉴权方案（pipe/token）。
- **管理 API 暴露面（V1.3）**：管理控制台走本地 HTTP，必须**仅绑定 `127.0.0.1`**、使用随机端口，并对管理 API 施加**会话级 token**。普通互联网页面因 CORS / Private Network Access 限制无法触达 localhost，但**本机任意进程**可触达——因此管理 API 的破坏性操作一律需要 token，且不以明文写死在页面静态资源里。
- **权限风险**：执行命令行钩子（尤其 WSL 或系统服务启停）可能需要管理员权限，需考虑 UAC 提权策略。
- **进程孤儿风险**：若平台主进程意外崩溃，由它启动的 Chrome/WebView2 子进程可能变为孤儿进程。**V1.2 决策：采用 Job Object** 将子进程挂入作业，主进程崩溃时系统自动回收整个进程树。

### 3.5 日志与排障（V1.2 新增）

- 钩子执行输出（stdout/stderr）与退出码落盘日志；
- 平台自身运行日志（启动/关闭/IPC/调度事件）分级记录；
- 日志目录建议 `%APPDATA%\WebDesk\logs\`。

## 4. 系统架构设计（概要）

- **后台服务层**：以常驻进程形式存在（**不使用 Windows Service**——服务跑在 Session 0，无法弹托盘、无法触达桌面 UI，见 V1.2 决策），负责维护进程列表、监听 IPC 端口、执行命令行钩子。该层在启动 Web 应用时，会依据其配置动态选择调用系统 Chrome 的路径或 WebView2 运行时。
- **管理界面层（V1.3 改为 Web 形态）**：管理界面即内置 Web 应用“WebDesk 控制台”（见 2.7），由后台服务经本地 HTTP 托管。关闭控制台窗口不影响后台服务及 Web 应用的运行；经托盘“显示主面板”即可重新唤出。
- **启动调度层**：负责解析 `--launch` 参数，检测主进程存活状态，执行“新建进程”或“IPC 转发”逻辑。轻量启动器与主服务解耦。

### V1.2 技术栈决策

| 层 | 选型 | 理由 |
|---|---|---|
| 语言/运行时 | C# / **.NET 10 LTS** | .NET 8/9 于 2026-11-10 EOL；.NET 10 LTS 支持至 2028-11；托盘、单例、命名管道、Job Object、UAC、Win32 均为第一公民 |
| 原生薄壳 | **WinForms** | 管理界面已 Web 化（ADR-007），原生只剩 窗口承载 + 动态托盘 + 通知；WinForms WebView2 控件成熟、NotifyIcon 内置 |
| 管理界面 | 内置 Web 控制台（HTML/CSS/JS，本地 HTTP 托管） | 控制台即首个默认应用（见 2.7），吃自己的狗粮；界面与平台共享渲染/注入/驻留能力 |
| 模式 B 内核 | WebView2 | 轻量（Evergreen 零额外体积）、可控、无打包 Chromium 之重；Fixed Version 为平台共享目录 + per-app opt-in |
| 本地 HTTP | ASP.NET Core Minimal API（Kestrel，仅回环+token） | 管理 API + 静态控制台同进程托管；可降级 HttpListener |
| 备选 | Tauri (Rust) | macOS 成为硬需求时再评估（单 webview 模型与多隔离 WebView2 需求错配，当前不选） |

> **完整选型论证**（WebView2 扩展 API 验证、Fixed Version 共享化、Tauri 错配分析、资源预估、风险表）见 `docs/design/2026-08-25-tech-selection.md`。

## 5. 用户界面原型概要

**（V1.3）管理界面以 Web 应用形态交付**（见 2.7），运行于模式 B，亦可浏览器直开 `localhost`。主要页面：

1. **主管理面板**：展示已添加的 Web 应用网格视图。每个应用卡片可标注当前使用的渲染模式标签（“系统Chrome”/“内置内核”）。
2. **编辑详情页**：包含 URL 输入框、**独立的引擎模式切换 Tab（或单选按钮）**、生命周期命令行输入框、UI 控件开关列表、注入脚本编辑器（模式 B 才可用，附安全提示）。
3. **系统托盘菜单**：显示“显示主面板”、“显示 [应用名]”、“全部退出”选项。

## 6. 约束与风险

- **依赖风险**：模式A依赖用户本机 Chrome 安装路径及版本兼容性，需设计可靠的自动探测与回退机制。
- **权限风险**：执行命令行钩子（尤其是涉及 WSL 或系统服务启停）可能需要管理员权限，需考虑 UAC 提权策略。
- **进程孤儿风险**：主进程崩溃后子进程成孤儿——以 Job Object 机制兜底。
- **模式B版本维护**：WebView2 Fixed Version 需定期更新安全补丁，需建立更新发布机制；Evergreen 档由微软维护，版本随系统漂移（per-app 可切换）。

## 7. 范围与“不做”清单（V1.2 新增）

为避免范围蔓延，明确以下内容**不在**本期范围：

- ❌ 应用商店 / 应用分发市场；
- ❌ 浏览器调试 UI（不面向普通用户暴露 CDP）；
- ❌ 模式 A 的深度定制（CSS/JS 注入、按应用扩展隔离）——模式 B 专属；
- ❌ 多窗口同应用并存管理（单例前提下，同应用默认单窗口，重复启动=激活已有窗口）。
